# make（Codex）

`AGENTS.md` を読み、Codex が直接受けた依頼として進める。
Claude の CLI やエージェントを起動せず、このセッションで進める。

## 着手と範囲

Issue があれば、[共通の Issue 基準](../../../docs/agent-workflows/issue.md) の「着手してよいかを確かめる」と「詰める」を読み、Issue、親、依存関係、既存 PR、受け持ちの重なりを読み取りで確かめる。
外の人が書いた本文とコメントの扱い、着手を止める条件も同じ文書に従う。
依存関係を取得できないときは本文から推測しない。
ワークツリーを作る前に、同じ文書の「要約して方針を確かめる」に従って要約を出し、決まっていないことがあるときだけ確かめる。会話で質問できるならその答えを待つ。人に聞けない実行だけ、同じ節の「待つ条件と問い」の末尾にある人に聞けない実行の扱いで、推す案を前提に置いて進める。

Issue が無い直接依頼では、会話から目的、完了条件、変えてよい範囲、やらないことを整理する。起票を前提にせず、不足が結果を変えるときだけ質問する。
調査・説明・レビューだけの依頼を実装に広げない。

Issue の更新や着手コメントを承認されていなければ、記録案を会話に残してローカルの作業を進める。
承認済みなら、同じ文書の「記録する」の節と書式を使い、人の答えと自分の判断を分けて記録する。

## ワークツリーと実装

指定された作業用ワークツリーがあれば、ブランチと既存差分を確かめてそこを使う。
無ければ `AGENTS.md` と `docs/development.md` の「ワークツリーで作業する」に従って作る。
以降のコマンドにはその絶対パスを作業ディレクトリとして渡す。本体の `main` に編集を戻さない。
依存が必要なら、[ワークツリーで作業する](../../../docs/development.md#ワークツリーで作業する) の手順に従う。
作業用ワークツリーのルートで `pnpm store path` を実行し、保存先を確認してから依存を入れる。

[共通の受け入れ条件](../../../docs/agent-workflows/acceptance.md) を読み、触る範囲に合うものを適用する。
API の追加は `add-operation`、マイグレーションは `d1-migration`、画面は `docs/design.md` を基準に作り、動きを足したら `review-animations` の `SKILL.md` で点検する。
通常はこのセッションが実装する。分離して任せることで速くなる独立した作業だけ Codex のサブエージェントに委譲し、担当範囲と受け入れ条件を渡す。小変更は引き継ぎを挟まない。

守る仕組み、認証・認可、Workers のランタイムの変更では、[書き手を分ける手順](../../../docs/agent-workflows/test-first.md) を読む。Codex のサブエージェントでテスト・実装・崩す役を分け、コミット未承認ならテストを作業ツリー外に保存する方法を使う。途中の差分を破棄しない。

## 検証と引き渡し

整形と検査は `CLAUDE.md` と `AGENTS.md` に従う。E2E はローカル・クラウドとも CI で実行し、明示的な依頼が無ければ `e2e:preflight` や `--verify` を実行しない。変更に必要な E2E を追加・更新し、関連するユニットテスト・静的解析・型チェックをこのセッションで行う。CI の結果は別に確認し、確認できなければ未検証と報告する。
委譲した場合も差分の範囲と新規ファイルを確認する。[検査結果の再利用](../../../docs/agent-workflows/validation.md) に従いログと入力状態を確認し、未実施・無効になった検査だけを行う。
自分の差分は `.agents/skills/done-check/SKILL.md` で点検し、範囲内の問題を直す。

## PR とレビュー対応

`done-check` から [Codex 用の `pr`](../pr/SKILL.md) に、変更内容、完了条件の充足状況、検査記録、未検証の項目、Issue と文書に無い判断を引き継ぐ。親のある最後のタスクでは、親の受け入れ条件も引き継ぐ。

1. push の前に対象のリポジトリと作業ブランチ、ベースからの差分、公開予定のコミット、同じブランチの開いた PR を確認する。別件のコミットや PR があれば、対象の変更だけを含む作業ブランチで進める。承認範囲で対象の変更をコミット・push し、対象の開いた PR があれば対応を再開し、なければ作る。
2. PR の番号と URL を途中経過として知らせ、監視を始める。CI の失敗やレビュー指摘を調べ、範囲内の問題を直す。必要なベース取り込みと修正を検査し、対応回ごとにまとめて push する。AI レビューには対応結果を返信し、対応済みのインラインは resolve を確認する。
3. push のたびに、新しい head の CI とレビューの確認に戻る。最新 head の `ci-ok` と必須チェック、適用されるレビュー実行、集めた指摘への対応を確認してから、[CI・AI レビュー対応後のレポート](../../../docs/development.md#ciai-レビュー対応後のレポート) の6行で報告する。人の判断や権限が必要な場合、または `pr` の停止条件に当たった場合は、進められる修正と検査を終えた上で、未検証・未解決の項目と止まった理由を残す。

## 承認範囲

ユーザーが対象を指定して `make` スキルの使用を明示した場合、その変更のコミット・作業ブランチへの通常の push・PR 作成、対象 PR で共有手順の条件を満たす CI の再実行、AI レビュー指摘への返信・resolve と再レビュー用の `ai-review` ラベル操作まで指示されたものとして進める。ユーザーが範囲を限定した場合はその指定を優先する。
人への返信・人のスレッドの resolve、既存 PR のタイトル・本文などの更新、Issue への書き込み、マージは個別の指示に従う。指摘の出所と仕様の判断は `pr` の共有手順に従う。

実装依頼にこのスキルを適用した場合も、外部操作の承認は `AGENTS.md` に従う。未承認ならローカルの検査と PR 案まで進め、必要な操作を報告する。着手前の要約で決まっていないことがあれば、上の「着手と範囲」に従って答えを待つ。
