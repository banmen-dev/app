# 今日の画面の A/B/C 追加計測（#1055）

2026-11-15（日本時間）。#1018・#1054 マージ後の main `1e58e61fcb4f5f146f5c9005e6ad67b64fef639d` に、この比較器だけを加えて測定した。

## 判断

**後回し表示の実装は保留を継続する。** 現行の `src/routes/[slug]/+page.ts` は `Promise.all([today, firstSteps])` で today を先に発行し、今回の「正順」に対応する。正順では3条件×2回の全6セルで C の load 相当の p50 が B より低く、その分位点同士の差は5.40〜12.73msだった。C の同一試行で主の完了後に残る待ちは p50 9.25〜11.03ms（約9–11ms）で、待ちを分離できることは確認できた。

逆順は現行の発行順ではなく、発行順の影響を調べる対照である。逆順の追加待ちはほぼ0となり、B/C の優劣も回・条件で入れ替わる。A に比べて B/C の主の完了が遅い逆順の結果は競合を示す診断材料だが、逆順の0を現行の正順での効果を否定する根拠にはしない。保留する理由は、正順の短縮が観測されていても、ローカル Worker/D1 の処理順、キャッシュ、時間経過の影響を分離できず、実運用での改善量を判断できないことに限る。

これは「後回しが不要」という結論ではない。逆順の微小値だけで Issue を閉じない。次は実運用に近い同時実行環境で API の処理とタスクの操作開始を測り、first-steps が表示開始を遅らせるかを確かめて判断する。画面・API・認証・DB スキーマの挙動は変更していない。Issue への結果の投稿は未実施。

## 条件と再現方法

Node 26.13.0 / pnpm 12.12.0 / Wrangler 4.153.0。Linux の同じクラウド環境で、2回を逐次実行し、各回は新しい使い捨て D1 と Worker を起動した。build・テスト・他の計測とは重ねていない。各条件・発行順・方式ごと温め2回＋20回、nearest-rank の p50/p95（ms）。1回目は A→B→C、2回目は C→B→A。発行順は各回とも正順→逆順なので、時間・キャッシュと発行順は完全には分離しない。予備計測は以下の表に混ぜていない。

```sh
pnpm exec node scripts/today-loading-bench.ts --fixture-at 2026-11-15T02:40:00.000Z
pnpm exec node scripts/today-loading-bench.ts --fixture-at 2026-11-15T02:40:00.000Z --reverse-modes
```

`--runs` と `--port` も指定できる（既定20回・9742、デバッガー9743）。リポジトリのルートで実行する。既存の [全画面計測](loading-bench-results.md) と同じ方式で動かす。`loadingFixtureSql`、`sessionInserts`、`isBenchHealth`、`trackServer` は共用するが、Wrangler 設定生成・起動待ち・API 呼び出し・後片付けを組み立てる処理はこの比較器に複製している。既存の比較器の実行条件を変えないため、今回の差分では共通モジュールへの切り出しを行わない。同じ基準時刻の `loadingFixtureSql` と seed を投入し、5,000タスク・履歴・進行中スプリントなどのデータを保つ。セッションの有効期限は実行時に生成する。`--fixture-at` は Worker の時計を固定しないため、後日の再現では直近完了や持越日数の集計が当日と同じとは限らない。既存の手元 D1 と本番は使わない。

各条件の開始前に first-steps の応答の形（出力スキーマ、role、手順の有無）を検査し、各試行でも全応答後に出力スキーマを検査する。条件表のロール・起票履歴・必須手順の説明は seed と fixture の内容および実装から確認したもので、内部の分岐を実行時に計測してはいない。空応答の `role: null` だけでは leader と member の分岐を区別できない。どちらの回も全試行成功。一般メンバーの利用開始時と完了後を分けているが、未所属の管理者（admin 分岐）、リーダーの利用開始時、招待だけの人、個人組織などは網羅しない。

## 測っている時点

- A: today のみ。従との競合を見る診断用であり、A/B の差を後回し実装の改善量にしない。
- B: today と first-steps を並列開始し、両方を待つ（現行の成功経路の待ち方）。
- C: 同じ2操作を並列開始し、today の完了で load 相当時点を記録。その後も従を回収・検証してから次の試行へ進む。

正順は現行 load と同じ today→first-steps、逆順は対照用の first-steps→today の発行順。A はどちらも today 1操作で、時間経過の対照になる。

「主」は群の開始から today の JSON 読み取り完了まで。「load相当」は B が全応答待ちから復帰する時点、A/C が主の待ちから復帰する時点。「全応答」は全要求を回収した時点。出力スキーマ検査はこれらの計時の後に行う。「追加待ち」は各試行の `max(0, 全応答 − 主)` の分位点で、分位点同士の引き算ではない。Promise の回収や時刻取得の微小なオーバーヘッドを含むため、A や逆順の0.01msを従の API 遅延とはみなさない。

これは Node から API を呼ぶ比較で、実際の PageLoad・ブラウザ描画の測定ではない。B/C は別の試行なので、その分位点の差も同一試行での短縮量ではない。人工遅延は加えていない。組織の枠の待ち、URL 直接表示、画面内遷移、app:today の再読み取り、表示後にタスクを操作できる時点は未測定。体感の短縮量は主張しない。従の未認証・失敗・再試行や古い応答の扱いは実装しておらず、この比較器で保証するものでもない。
