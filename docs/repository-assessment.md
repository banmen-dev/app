# Banmen の現状と改善候補

調査日 2026-11-21。対象は Todos 上の `scrum-guild` の作業開始時点（`367b32b`）。
ソースコード、仕様、テスト、開発と運用の設定を照合した。
このプロジェクトで開発を続けるなら、最初に変更の検査方法を決めるのがよい。
既存の GitHub Actions にはテストやリリースの手順が揃っているが、Todos 上の変更に対してはそのまま起動しない。

## 改善候補と着手順

候補は、担当を割り当てて完了条件を一つずつ確かめられる粒度にした。
**先に**はこのチームでの開発開始に関わるもの、**次に**は既存の仕様や計測で課題が見えているもの、**必要時**は関連する変更に合わせて扱うものを指す。
担当は合意済みの役割分担に沿った案で、履歴にある Issue 番号は既存の仕様や計測を参照するために示した。

### 1. Todos 上の変更を検査できるようにする

**先に。Developer が検査の実行方法を整え、Reviewer が結果を確認する。**

`AGENTS.md` は E2E を CI で実行し、セッション内では明示依頼がある場合だけ実行すると定めている。
現状の CI は GitHub の PR や push を起点とする。
Todos ホストには組み込みの GitHub Actions 相当の仕組みがなく、PR の `ci-ok` や E2E の結果を前提にした完了判定をこのプロジェクトへそのまま持ち込めない。
別の実行環境や連携の有無は未確認。
[Codex の作業ルール](../AGENTS.md) / [CI の起動条件](../.github/workflows/ci.yml) / [Todos ホストの仕様](https://todos.dev/docs/platform-git#differences-from-a-github-project)

完了条件は、変更対象のコミットを指定して既存の型、lint、ユニットテスト、マイグレーション、必要な E2E を実行でき、Reviewer が同じコミットの結果と失敗ログを Todos の変更レビューから確認できること。
まず検査を対象にする。
このリポジトリから本番リリースも扱う場合は、既存の Release と Workers Builds の接続先を確認する仕事を別に切り出す。

### 2. 開発を始める入口を README に置く

**先に。Quick fixer が担当できる。**

要件には日本語の README を置く方針があるが、ルートに README がない。
現在の入口は `CLAUDE.md` と `AGENTS.md` で、製品の説明、必要な Node と pnpm の版、起動と検査、データベースの初期化、ホストごとのレビュー手順を複数箇所から探す必要がある。
[初版の要件](requirements.md#初版) / [全体の案内](../CLAUDE.md) / [開発手順](development.md)

完了条件は、初めて開いた人がルートから概要、セットアップ、開発時の基本コマンド、仕様と運用文書にたどり着けること。
seed を入れ直すと手元の D1 の行が消える点も、実行する前に分かるようにする。
Todos 固有の検査手順は候補1で確認した内容へリンクし、共通のコマンド一覧は原本へ案内する。

### 3. 低速回線で初回に出る失敗表示を調べる

**次に。Developer が担当し、Reviewer が再計測を確認する。**

直近の計測記録では、初回表示までの転送量と件数は目標内に収まった。
同じ最終計測の Slow 3G では、2試行とも失敗表示を経て画面が開いた。
既存の改善で転送量は下がっているため、次はどの読み込みが失敗表示を出し、その後どのように復帰したかを計測する。
[初回表示の最終計測](benchmarks/boot-transfer-1236.md#追加修正main統合後の最終計測)

完了条件は、同じ経路と回線条件で現象の再現有無、表示を出した処理、画面が開くまでの時系列を記録できること。
修正を別に起票する場合は、再現した条件で一時的な失敗表示を抑え、本当の失敗時には案内と再試行が働き、既存の転送量の条件を保つことを受け入れ条件にする。

### 4. 請求専用の担当者が契約と使用量を確認できるようにする

**済み（#1241）。権限の点検は Reviewer が続ける。**

請求管理者の指名、承諾、交代と履歴は実装済み。
請求画面の読み込みは担当組織と管理者一覧、変更履歴を取得する。
契約や添付使用量を読む既存の `organizationInfo` は、組織に所属する業務側の管理者向けに制限している。
請求専用の担当者への契約と使用量の表示は #1241 で、組織管理者向けの `organizationInfo` を使わず、請求専用の読み取り（`billing-organization-summary`）として足した。
[契約と支払いの方針](business.md#契約と支払いの管理) / [請求画面の読み込み](../src/routes/auth/billing/+page.ts) / [組織側の取得処理](../src/server/operations/organization.ts)

完了条件は、承諾済みの請求管理者が担当組織の契約、上限、必要な使用量を確認でき、未承諾、解除済み、別組織のアカウントでは取得できないこと。
業務データへの権限は請求管理者の付与から独立させる。
決済連携の #1242 は別の作業として扱う。

### 5. バックログの読み込み順は変えない

**済み。#1056 は 2026-11-23 に実装せずに閉じた（not planned）。**

#1056 では、一部の経路で操作可能になるまでの時間が短くなった一方、同規模の悪化が観測された条件もあり、読み込み順の変更は保留になった。
報告には実行順やキャッシュ、時間経過の影響を分離しきれていないという限界もある。
その後、#1432 で待たずに済ませる候補の取得が1つになり、見込める短縮が揺れより一桁小さくなったので、測り直さずに閉じた。計測器は #1479 で消した。
待たずに済ませる取得が重くなる変更があれば、別の Issue で扱う。
[バックログの計測結果](backlog-loading-browser-results.md#2026-11-17-の結果) / [#1056 の結論](https://github.com/banmen-dev/app/issues/1056#issuecomment-7098452355)

### 6. タスク詳細の変更では、触る責務を絞る

**必要時。履歴表示を変更する際に Developer が担当し、Reviewer が画面遷移に伴う回帰を確認する。**

タスク詳細の `TaskDrawer.svelte` は、編集中のまま閉じる場合の処理、属性編集、添付、履歴の初回取得と追加取得を一つのコンポーネントに持っている。
履歴の再取得は複数の更新処理から呼ばれるため、表示の修正でも保存後に履歴が更新される条件を追う必要がある。
属性編集はすでに独立したモジュールとテストを持っている。
[タスク詳細](../src/lib/components/TaskDrawer.svelte) / [属性編集のテスト](../src/lib/task-attributes.svelte.test.ts) / [詳細の再読み込みの E2E](../e2e/task-drawer-refresh.test.ts)

完了条件は、履歴を触る変更で取得状態と追加取得の責務を小さく切り出せるかを確認し、変更する場合は初期表示、再試行、追加取得、タスク切り替え後の表示、保存後の再取得を検査できること。
現時点では保守上の候補で、これを理由に画面全体の分割を先行させる必要はない。
