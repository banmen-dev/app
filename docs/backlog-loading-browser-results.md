## 計測時のコードを復元する

基準コミット `ab2588b250ee4ffc13a876b30216cfe68c6ae22d` の検証用checkoutを別の場所に用意し、保存した実行コードをその `scripts/` に書き出す。以下の第2引数は用意済みのcheckoutの絶対パスに置き換える。既存の共通ヘルパー・製品ソース・依存は基準コミットから復元する。現在の作業コピーを上書きせず、計測時の版と現行版を区別する。

```sh
node --input-type=module - docs/backlog-loading-source.json.gz /tmp/backlog-loading-measured <<'JS'
import { readFileSync, writeFileSync, mkdirSync } from 'node:fs';
import { gunzipSync } from 'node:zlib';
import { resolve } from 'node:path';
const snapshot = JSON.parse(gunzipSync(readFileSync(process.argv[2])).toString('utf8'));
const scripts = resolve(process.argv[3], 'scripts');
mkdirSync(scripts, { recursive: true });
for (const [name, source] of Object.entries(snapshot.files)) {
  if (!/^backlog-loading-[a-z-]+\.ts$/.test(name)) throw new Error('不正なファイル名');
  writeFileSync(resolve(scripts, name), source);
}
JS
```

これはコードと計測方法を復元する手順であり、別時刻・別環境でも同じ応答時間になる保証ではない。保存済みの数値と採否の再現には上の再集計の入口を使う。

## 架空データと操作の定義

公開 seed の member セッションで、新しい架空組織の一般メンバーを読む。非空の作業場は100タスク・2エピック・4ストーリー、区分とリポジトリ各1件。別の作業場は本当に空。対象タスクは初回から表示する親なしの行に固定する。5万件の上限計測は既存の `bench:backlog` の範囲で、今回の結果へ混ぜない。

| 条件 | URL の絞り込み | 指標 |
| --- | --- | --- |
| 絞り込みなし | なし | 対象タスクの操作開始 |
| 自分と検索一致 | assignee=me、q=計測対象 | 対象タスクの操作開始 |
| 区分とリポジトリ一致 | fixture の区分ID・リポジトリID | 対象タスクの操作開始 |

| 検索該当なし | q=存在しない検索語 | 該当なしの案内の表示 |

ブラウザは1280×900、ja-JP、Asia/Tokyo、gzip、HTTPキャッシュ無効・service worker無効。回線制限・人工遅延なしのループバック。各条件・方式・発行順を独立セルにし、温め2回の後に20回記録する。2巡目は新しい D1 に同じ fixture を入れ、方式と組み合わせの順も反転する。ビルドは前もって済ませ、他の build・検査・計測とは重ねない。

| 経路 | 開始と終点 |
| --- | --- |
| 直接表示 | URL へ文書全体を開く navigation start から測る |
| 画面内遷移 | 同じ組織のプロフィールへ SPA で移って全通信を回収し、バックログへのリンク操作開始から測る |
| 再読み取り | 実際の invalidate('app:backlog-tree') を計測専用イベントから呼ぶ時点から測る |
| 絞り込み変更 | 別の検索条件の木を読み終えた後、実際の applyFilter を呼ぶ時点から測る。入力・300ms debounce の時間は含めない |

各経路で、描画された filter と readVersion の更新を確認する。特に再読み取り・絞り込み変更は前の木を押せたことを成功にしない。新しい木の描画後2フレームを待ち、固定タスクの完了ボタンの trial click が成功した時点を操作開始とする。クリック到達性の確認であり、完了を実行したり保存完了時間を測ったりしない。空の2条件は空の案内が見えた時点を測り、採用根拠にしない。

区分・リポジトリの選択肢は、一覧の状態反映と実際の select の選択肢・有効化を別の並行処理で確認する。その確認時点を choices として記録し、操作開始の待ちには足さない。本当に空の作業場では選択欄自体を描画しないため、choices は一覧の状態反映の確認時点であり、選択可能時点ではない。組織・ワークスペースの枠の API 完了も別記する。新たな枠の要求が無い経路の0は、既に読んだ枠の再取得を待っていないことを示し、枠の初回表示が0msという意味ではない。

## 解釈の限界

ローカル Worker/D1 の直列処理、実行順、キャッシュ、経時変化を完全には切り分けられない。正逆順の差や1巡だけの差を因果的な改善・悪化と断定しない。HTTPキャッシュ無効でも、同じ context のメモリ・JIT・SPA の利用条件は経路ごとに異なる。ブラウザの確認処理自体の時間も含むため、確認時点は内部描画の厳密な最早時点ではない。全条件は一般メンバーで、他のロール・個人用組織・大規模データ・実運用の同時実行へは外挿しない。

C は成功経路の性能試作であり、製品の認証・失敗表示・再試行・古い401の処理を実装済みとは扱わない。追加の製品実装は合意した採用基準を満たす場合だけ行う。測定不能や通信失敗は正常試行に混ぜず、未完了の報告は再集計器が拒否する。
