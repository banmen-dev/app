# エピック詳細のブラウザ計測の追試（#1058）

PR #1412 の計測とは別に、基準コミット `61fc0ae`、Chromium 155、ブラウザ内の描画フレームによる観測で実施した独立計測。両計測とも改善基準は未達だった。試行の分位点と悪化の件数は実行ごとに記録する。 [PR #1412 の計測結果](epic-loading-browser-results.md)

**製品変更は保留し、Issue を継続する。** 正式計測の全360件が完了し、欠測・通信失敗は0件。詳細ページで区分の一覧を外す C は、「直す」の操作開始 p95 が A より100 ms以上かつ10%以上改善し、両巡で再現した経路がなかった。正式指標全18組のうち、同じ規模で遅かったのは1巡目の5組。直接表示の詳細表示と操作開始、再読み込みの3指標が該当した。

例えば再読み込みの操作開始 p95 は、1巡目に 802.1 → 920.3 ms、2巡目に 952.5 → 854.2 ms。2巡目の短縮は98.3 msで、100 msに届かなかった。巡によって差の向きも変わったため、C が遅くなる因果関係はこの計測から判定できない。

基準コミット `61fc0aedfccc07f822899cad9bd1e533fff3124b`。2026-11-22 18:31〜18:47（日本時間）、Linux x64、Node v26.13.0、pnpm 12.12.0、Wrangler 4.153.0、Chromium 155.0.8059.79。計測中は他のビルド・検査・計測を止めた。読み取りの正式計測後、C で引き出しから本文を保存し、`app:epic-detail` の再読み取りで詳細に反映されることを確認した。一時 D1、配信用ビルド、起動プロセスを片付けた。

展開した生データの SHA-256 は `cd932c37c002a87ecbefcabd424ba905b04f429f6759c3de29e5569723ffb99d`。計測コードと seed の入力ハッシュは生データの `inputHashes` に記録した。

## 比較条件

| 方式 | 詳細ページの取得と待ち方 |
| --- | --- |
| A（現行） | `epic-detail` と `category-repository-list` をこの順で並列開始し、両方を待つ。 |
| B | 同じ順で両方を開始し、`epic-detail` を待つ。 |
| C（製品候補） | `epic-detail` を取得する。 |

3方式で詳細の区分名は `epic-detail` の値を使う。引き出しの操作と `epic-get`・区分の一覧取得は共通。A は現行の load を使い、B/C は計測専用のビルド変換を使う。開発用の架空 seed にある受託開発チームを一般メンバーで開く。対象は「ポイントの交換先を増やす」。配下のストーリー1件、参加者2名、選択肢は区分・リポジトリ各2件で、対象には「追加案件」を設定済み。固定の架空データの基準日は 2026-11-22。

| 経路 | 起点 |
| --- | --- |
| URL直接表示 | 新しい文書の navigation start。 |
| 画面内遷移 | バックログでエピックの引き出しを開いて準備を済ませ、引き出し内の「エピックの画面を開く」をクリックした時点。 |
| ブラウザ再読み込み | 詳細を表示して通常のリロードを行い、新しい文書の navigation start。 |

- 詳細表示は見出し・区分名・本文が描画された時点。「直す」の操作開始はリンクが表示され、クリック位置で入力を受けられる時点。独立したフレーム内の観測で時刻を記録する。
- 「直す」を実際に押し、引き出しの区分一覧が読めて、現在値を保持し別の区分を選べる時点を測る。起点からと、押下からの2つを記録する。押下からの時間と各 API の開始・完了は診断用。
- 各方式・経路で温め2回と記録20回。巡ごとに新しい使い捨て D1 を作成し、方式と経路の順を反転する。Chromium は試行ごとに新しいコンテキスト。HTTP キャッシュとサービスワーカー、先読みを無効にし、1280×900、日本語、Asia/Tokyo、ループバックの gzip 配信を使用した。
- 各試行で詳細ページと引き出しの API の発行数をそれぞれ検査し、時刻の確定後に全応答を回収して HTTP・JSON スキーマと画面例外を確認する。少数回の予行の試行は正式結果から除いた。
- 実行環境はローカル Worker/D1 で、API の並行実行や処理順、回線待ちが実運用と異なり得る。同じ集計を実運用に近い同時実行条件で確認する余地がある。p95 は昇順19番目で、少数の遅い試行の影響を受ける。

## 再現と再集計

追試の[生データ](epic-loading-replication-samples.json.gz)、[採否とセルごとの集計](epic-loading-replication-decision.json)、[計測ソース](epic-loading-replication-source.json.gz)を保存した。

```sh
# 現行リポジトリから復元する。空いているパスを使う。
repo=$(git rev-parse --show-toplevel)
replay=$(mktemp -d)
git -c core.hooksPath=/dev/null worktree add --detach "$replay/checkout" 61fc0aedfccc07f822899cad9bd1e533fff3124b
python3 - "$repo/docs/epic-loading-replication-source.json.gz" "$replay/checkout" <<'PYTHON'
import gzip, json, re, sys
from pathlib import Path

snapshot = json.loads(gzip.decompress(Path(sys.argv[1]).read_bytes()))
checkout = Path(sys.argv[2])
for path, source in snapshot['files'].items():
    if not re.fullmatch(r'scripts/epic-loading-[a-z.-]+\.ts', path):
        raise ValueError(path)
    with (checkout / path).open('x') as output:
        output.write(source)
PYTHON
gzip -dc "$repo/docs/epic-loading-replication-samples.json.gz" > "$replay/recorded.json"
cd "$replay/checkout"
pnpm store path
pnpm install --frozen-lockfile --store-dir "$PWD/node_modules/.pnpm-store"
pnpm exec node scripts/epic-loading-summary.ts "$replay/recorded.json" "$replay/summary"
```

新しく測る場合は復元先で `pnpm exec node scripts/epic-loading-browser-bench.ts --output "$replay/new.json"` を実行する。Chromium は Playwright の配布版を用意するか `--chromium` で指定する。ポート9764〜9766を使う。採否基準は [Issue #1058](https://github.com/banmen-dev/app/issues/1058) を参照。
