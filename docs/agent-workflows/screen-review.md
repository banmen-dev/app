# 画面の自己レビュー

Playwright で実装と見本の同じ状態を撮り、独立した採点役が `docs/design.md` の「デザイン原則」と「どのテーマにも共通すること」と照らす。進行役が撮影、差分の調査、修正、再撮影を担当する。画面採点の周は `done-check` のコードレビューの巡と別に数える。

## 対象を決める

| 画面 | 状態 | 実装の URL | 状態を作る操作 | 見本 |
| --- | --- | --- | --- | --- |
| `today` | `list` | `/aoba` | seed の管理者で開き、既存タスク1件に「今日やる」の印を付けて読み直す | [今日やることの一覧](../../design/today.html) |

- 差分が触った状態だけを選ぶ。新しい画面は登録した全状態、全画面に効く差分は登録した全状態を選ぶ。
- 一覧、空、ダイアログなどの対応を1状態ずつ登録する。対応する見本と、状態を作れる正規の画面操作か API が揃ったら、`scripts/screen-review-options.ts` の引数と `scripts/screen-review.ts` の撮影処理に登録する。見本に新しい種類の資産があれば `scripts/screen-review-runtime.ts` の MIME 型も確認する。seed にないデータはその操作で作る。

## 撮影する

作業用ワークツリーで `pnpm screen-review <画面> [<状態>...] [--round <1–3>] [--exclusions <path>]` を実行する。周の既定は1で、状態を省くとその画面の登録済みの全状態を撮る。初回は `pnpm screen-review today list` で撮れる。

- 開発サーバーのポートは `pnpm dev` と同じ決め方に従う。既に使用中なら、自分で起動した同じワークツリーのサーバーを止めるか、`DEV_PORT_OFFSET` で空いているポートにずらす。
- コマンドは撮影専用の開発サーバーと使い捨てのローカル D1 を使う。seed を流してから専用のブラウザに seed のセッション Cookie を置き、テーマをマイプロフィールの API で保存する。見本のテーマは `sq-design-theme` に置く。用語はスクラムの言葉に固定する。seed、Worker、ブラウザの日付は直近の水曜10時（日本時間）に揃え、`capture.json` に時刻を記録する。
- `simple_light`、`simple_dark`（シンプルのライト、ダーク）を、PC 1280×900 とスマホ 390×844 で撮る。両方の画面で `innerWidth` とテーマが合い、目的の状態が表示されていることを確かめる。幅が異なれば1回撮り直し、再び異なれば失敗とする。
- 2テーマの PC 幅で、タスクを完了したときの判子とトーストを実操作で起こしてコマを撮る（エピックのクリアの演出は #1434 で外した）。動きを減らす設定でも同じ操作を行い、演出が止まることを検査する。
- Chromium がなければ Playwright の Chromium の導入を試みる。既に導入済みのシステム Chromium を使うときは `SCREEN_REVIEW_CHROMIUM` に実行ファイルのパスを指定する。

成果物は `screen-review-results/<画面>/<状態>/<周>/` に書かれる。E2E が実行時に消去する `test-results/` の外なので、撮影結果は次の E2E 実行後も残る。撮影に失敗したら、そこで得られた画像と失敗理由を周の `failed-*/` に残す。強制終了後にロックが残ったら、同じ周を撮影しているプロセスが無いことを確かめる。自分で起動した Vite と Wrangler が残っていれば、それらだけを停止し、対象の周の `.capture-in-progress` を削除してから撮り直す。失敗画像は調査に不要になった周の `failed-*/` を手元で片付ける。

撮影の完了は次を確かめて判定する。

- `originals/` に実装と見本の PNG が各6枚ある。テーマと幅の全組を `capture.json` で突き合わせる。見本で外部フォントの読み込みに失敗した条件は `referenceFontFailures` に残り、対の画像の見本側に「フォント未確認」が出る。文字の採点がフォントに左右される条件は、ネットワークを確認して撮り直す。
- `pairs/` に実装と見本を左右に並べた画像が全6組あり、長い画面は縦に分割しても文字が読める。人が全条件を見渡すための `contact-sheet.png` がある。
- `motion/` に連続コマの画像と、動きを減らす設定の検査結果 `results.json` がある。

## 採点して直す

1. 進行役は周の `pairs/` の画像、`motion/` の合成画像、撮影時の `design-rules.md`（`docs/design.md` の「デザイン原則」と「どのテーマにも共通すること」の抜粋）、テキストの `exclusions.md` を、独立した採点役1体に絶対パスで渡す。全組の比較と前後のコマが見えることを確認する。採点の根拠には、これらの資料だけを使う。
2. 採点役は観点ごとの1〜10点と画像の根拠、悪い順に最大3件の指摘を返す。進行役はその報告を受け、修正の許可範囲にある指摘を直す。画面の外に原因があるものは、進行役がコードを確認して除外できる。除外一覧には1件ずつ、画面・状態・テーマ・幅、画像内の箇所、指摘の文、原因のコードのパスと画面外と判断した理由を書く。既存 Issue があれば番号を添える。根拠がそろっていない指摘は除外しない。
3. 修正や除外があれば次の周を撮って採点する。除外を渡すときは `--exclusions` で前の周にまとめた一覧を指定する。除外に一致する指摘が次の周の採点と上位3件から外れていることを確かめる。
4. すべての観点で8点以上なら合格。3周で届かなければ停止し、点数と残件を記録する。3周目の採点後に画像が古くなる修正を加えた場合は、その修正を再採点していないことを引き渡す。

## 引き渡す

PR の `## 画面の自己レビュー` に状態、最終周のコンタクトシート、観点ごとの点数、直した指摘、除外の適用件数と各件の条件・内容・根拠（適用0件も明記）、一致しなかった除外、残件を書く。新しい画面ではこれを画面の証跡とする。作成環境で画像を貼れない場合は、成果物のファイル名と手元で貼る画像を記す。未実施や中断はその理由と、手元で行う確認を記す。レビューを回せなかった PR は `needs-human` として扱う。

ループの後で、画面の外に切り出した指摘について既存 Issue を探す。既に該当するものがあればその番号と追記する内容、無ければ部品ごとの起票案を引き渡す。GitHub へ書き込むときは進行役の製品の手順と承認範囲に従う。Codex で PR やラベルの操作が未承認の場合は、PR 草案に `needs-human` の要否と理由を残す。
