# 計画の主・従の追加比較（#1057）

2026-11-15（日本時間）。測定時の基準 main `4f3efe5` と本差分の計測器。測定後に main `4706de8` のフック修正を取り込んだが、測定入力は変わらないため再測定していない。Node 26.13.0 / pnpm 12.12.0 / Wrangler 4.153.0。

## 結論

後回しの画面実装は保留する。B と C は同じ通信を発行し、同じ readTrial で全応答を回収する。違うのは返却モデルを全応答完了（B）と主完了（C）のどちらに置くかだけであり、B/C の主完了は同じ分布を測っている。別試行の B/C の主完了の差は、試行のばらつき・条件の実行順・時間経過などのノイズで、待ち方の効果とは読めない。「C が遅くなった」という実装上の悪化は、この測定からは主張しない。

正順では従が後に完了するため、全応答完了と主完了の返却モデルに差が出る。今回の逆順の表では、各条件内の主完了と全応答完了の分位点が一致している。ただし、逆順は従を先に発行するだけであり、完了順や両時刻の一致を保証しない。B/C の主完了の別試行差を条件の効果と読めないのは、同じ通信を別々に測っているためであり、発行順による完了順の保証を根拠にはしない。これは発行順に依存した API 完了時刻の診断であり、表示・操作開始の改善を測ったものではない。A と B/C は通信数も違うため、従との競合の診断に限定する。実環境の改善根拠としても、不要として Issue を閉じる根拠としても使わない。

履歴あり・管理者の返却モデル p50/p95（ms）は、1回目の正順 B 30.98/36.73 → C 14.94/29.69、逆順 B 29.02/34.11 → C 28.54/32.12。2回目の正順 B 35.52/37.96 → C 17.95/22.74、逆順 B 36.10/43.44 → C 38.04/58.64。これらは別試行の分位点である。逆順の B/C の差は同じ通信を別に測ったノイズで、条件の効果とは読めない。正順も別試行の分位点の差を各利用者の短縮量とは扱わない。

## 条件

- A: sprint-list のみ。従との競合の診断用で、改善量の比較対象ではない。
- B: sprint-list と plan-summary を並列開始し、両方を待つ現行の依存関係モデル。
- C: 同じ2操作を並列開始し、主だけを待つ依存関係モデル。主完了を返却モデルの時刻とする。実際の PageLoad を変更・実行した測定ではない。
- 各条件・利用者・発行順で温め2回＋20回。1回目は A→B→C、独立した使い捨て D1 の2回目は C→B→A。正順・逆順をそれぞれ測り、次の試行へ進む前に従を含む全応答を回収し、HTTP と出力スキーマを検査する。全 API が成功した。
- A/C の「主」と「返却モデル」は同じ値になる。B/C は同じ通信なので、返却モデルの違いだけを確認するなら各試行内の主完了と全応答完了を比較する。
- 主完了、返却モデル、全応答完了を共通開始時刻から測る。分位点は nearest-rank。単位 ms、各セル p50 / p95。各セルは20回の小標本で、p95 は昇順19番目（上から2番目）の値となるため、少数の遅い応答で大きく変わりうる。分位点の差を安定した条件の効果とみなさない。
- loading-fixture の履歴あり（タスク5,000・エピック10・ストーリー100・進行中1スプリントと未完了30件・終了3スプリントと直近7日の完了履歴）と、同じ組織の別の空ワークスペースを使用。両方を管理者と一般メンバーで測る。
- 先のスプリントがある条件、終了済みワークスペース、異なる履歴量は今回未計測。今回の条件からそれらへ効果を広げない。
- ブラウザ、URL直接表示・画面内遷移・invalidate、親の組織とワークスペースの枠、ネットワーク遅延、キャッシュの影響は分離・計測していない。体感の短縮量は主張しない。
- 他の build・テストと重ねていない。既存の D1 と本番を使わず、各回終了時に一時 D1 とサーバーを破棄した。

## 再現

#1057 を閉じた後、専用の計測器を削除した。再現するときは、測定時の基準コミット `4f3efe5` のワークツリーに [PR #1253](https://github.com/banmen-dev/app/pull/1253) の計測器を取り出す。現在の作業コピーのリポジトリルートから次を実行する。

```sh
git -c core.hooksPath=/dev/null worktree add --detach worktrees/1057-api-repro 4f3efe5
cd worktrees/1057-api-repro
git restore --source=c1d9c52ab3a3d78428112ac93d4de82c2b871d15 -- scripts/loading-bench.ts scripts/plan-loading-comparison.ts
```

依存は [ワークツリーで作業する](development.md#ワークツリーで作業する) の手順に従って入れ、同じワークツリーで次を実行する。

```sh
pnpm bench:loading --plan-compare
pnpm bench:loading --plan-compare --comparison-reverse
```

書き込み先が制限された環境では `XDG_CONFIG_HOME` と `WRANGLER_LOG_PATH` に書ける一時ディレクトリを指定する。このセッションでは `/tmp/1057-config` と `/tmp/1057-wrangler-logs` を使い、`WRANGLER_SEND_METRICS=false` とした。初回の起動失敗は計測結果に含めていない。

レビューで計測器の分岐・利用者指定・集計処理を整理した後、`--plan-compare --comparison-reverse --runs 1` を実行し、両データ・両利用者・正逆順の全条件の HTTP/出力スキーマと一時 D1 の破棄を確認した。この少数回の確認値を下表の測定結果に混ぜていない。

## 次に必要な判断材料

実運用に近い同時実行条件とブラウザで、主の表示・操作開始に plan-summary の待ちが乗るかを確認する。URL直接表示・画面内遷移・app:sprints / app:backlog-tree の再読み取りを分け、親の待ちと主・従の待ちを分離する。先のスプリントや終了済みワークスペースも条件に加える。ローカルの同じ比較を繰り返すだけで適否を確定しない。

load が従の Promise を返す方式と部品のマウントで取得する方式は、今回どちらも採用していない。採用判断と現在の状態は [Issue #1057](https://github.com/banmen-dev/app/issues/1057) を正とする。
