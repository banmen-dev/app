## 架空データの条件

seed の公開 member セッションを使い、6つの独立した架空の組織を追加する。組織ごとのロール・手順の有無・タスクの有無を計測前に検証する。

| 条件 | 手順 | タスク | 理由 |
| --- | --- | --- | --- |
| member / pending | あり | 5,000件中30件に今日の印 | 他の人が起票し、本人が担当する。本人の prepare_task は未完 |
| member / completed | 空 | 同上 | 本人の起票で prepare_task が完了 |
| leader / pending | あり | 空 | バックログに1件でもあれば必須完了となるため、タスクありの組み合わせは成立しない |
| leader / completed | 空 | 5,000件中30件に今日の印 | バックログにタスクあり |
| admin / pending | あり | 空 | 組織に作業場がなく、最初の作業場を作る手順が未完 |
| admin / completed | 空 | 空 | 作業場は作成済み、本人に所属なし。作業場に所属すると member/leader 分岐へ移る |

## 解釈の限界

ローカル Worker/D1 の実質直列処理、キャッシュ、経時変化を完全には切り分けない。逆順は発行順の診断で、現行の正順の効果を否定する根拠にしない。直接表示と画面内遷移は HTTP キャッシュ無効だが、同じ context のメモリや SvelteKit のデータ利用条件まで等しくはならない。一般メンバーの結果を他の利用者や本番へ無条件に広げない。

試作 C の待ちの分離が働いても、合意したブラウザ基準を満たさなければ製品へ採用しない。分離できない影響が判断を左右する場合は実運用に近い同時実行環境での追加計測が必要。人工遅延は待ちの分離を検証する用途に限る。
